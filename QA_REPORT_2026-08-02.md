## Bug #3: AI switches to Demo unexpectedly + Bug #2: Stop button regression

**Same root cause — fixed once, as requested.**

### Root cause

Both `sendMessage()` and `stream()` in `orchestrator.service.ts` had a
per-candidate `catch` block that called `this.health.recordFailure(candidate.key)`
**unconditionally** — on any thrown error, with no distinction between a
genuine provider failure and an `AbortError` produced when the user clicks
Stop.

Every time Stop was tested against Gemini, OpenAI, or Anthropic mid-request,
that provider's failure counter in `ProviderHealthService` incremented
exactly as if the provider had actually broken. After 3 such cancellations,
the circuit breaker (working exactly as designed) deprioritized that
provider for 30 seconds. Combined with Ollama not actually running locally
in the test environment, this produces precisely the observed:
```
"ollama" wasn't available — used "demo" instead.
```
— not a routing bug, but a healthy provider being punished for the person
testing the Stop button.

### Fix
Both catch blocks now check `signal?.aborted` before recording a failure.
A cancelled request breaks out cleanly (non-streaming) or returns
immediately (streaming) without touching the health tracker or yielding a
spurious error event.

### Verification — real executed code
- 4 new tests in `orchestrator.service.spec.ts`: aborting `sendMessage()`
  and `stream()` individually, **3 consecutive cancellations in a row**
  (would have tripped the old 3-failure threshold), and a contrast test
  proving genuine provider failures still correctly mark a provider
  unhealthy after 3 real failures.
- A final closed-loop check: simulated 3 real Stop-button clicks against a
  provider, then sent a normal "Hello" — **confirmed it still used the
  real provider, not Demo** (this is the literal reproduction of the
  reported bug, now fixed).
- `npx jest`: all passing, including these.

## Bug #1: Large file upload hangs forever

### Root cause

Express's JSON body-parser defaults to a **100KB** limit whenever it's not
explicitly configured — and it never was in this app. `storage.controller.ts`
advertises (and enforces, in its own code) a 15MB attachment limit, but
that check never ran for anything past a certain size: base64 encoding
inflates a file by ~33%, so any file whose base64 JSON payload exceeds
100KB gets rejected by Express itself, **before our own controller code
ever executes**.

I found the exact threshold empirically against a real Express server
(not guessed): **74KB succeeds, 75KB fails with a 413.** A person
reporting "~60KB" is very plausibly describing a file in the 70-80KB
range (file-size estimates are rarely exact), which lands right on this
undocumented cliff edge.

**A compounding bug found in the same investigation:** `HttpExceptionFilter`
forced *every* non-Nest-`HttpException` error to a generic 500 — even ones
(like Express's `PayloadTooLargeError`) that carry their own valid 4xx
status. So even once identified, this would have surfaced as a confusing
generic 500, not a clear "file too large" message.

### Fix
- `main.ts` now explicitly sets `app.use(json({ limit: "21mb" }))` and the
  equivalent for urlencoded bodies — comfortably covering a 15MB file's
  base64 form plus JSON/field overhead, actually matching the app's own
  advertised capacity.
- `HttpExceptionFilter` now trusts a non-Nest error's own status code when
  it's genuinely in the 4xx range (deliberately **not** 5xx — a library
  error claiming its own 5xx status isn't necessarily trustworthy the way
  a framework-level 4xx parsing rejection is), and gives a curated,
  specific message for 413s instead of a generic fallback.

### Verification — real executed code
- 3 new tests in `body-size-limit.spec.ts` (real Express server, not
  mocked): the exact 100KB-default rejection reproduced at 80KB, the same
  request succeeding under the fixed 21MB limit, and a full **15MB file**
  (the scenario the limit exists for) succeeding end-to-end.
- 4 new tests in `http-exception.filter.spec.ts`: the 413 case reported
  correctly, a genuine 500 staying 500 with its message still hidden, a
  suspicious non-Nest 5xx claim still forced to 500 (not trusted), and a
  real Nest `HttpException` completely unaffected.

## Bug #4: Three-dot loading indicator never stops

**Not independently reproduced as a distinct new bug this session.**

I re-traced the full completion path fresh (per the instruction not to
assume prior fixes still hold): the SSE `done` event → `runStreaming()`'s
dispatch → `status: "complete"` → the indicator's render condition. Found
nothing newly broken in this chain (the double-wrapping bug that caused
this exact symptom was already fixed in the prior session and remains
fixed — re-verified via the existing `sse-wire-format.spec.ts` and
`transform.interceptor.spec.ts`, still passing).

**Best-supported explanation:** a downstream symptom of Bug #2/#3's root
cause. Before the health-service fix, a turn could cascade through several
failing candidates (each bounded by a real timeout, default 30s) before
reaching Demo — a real, if bounded, delay that could plausibly read as
"stuck loading" to someone testing quickly, especially stacked with
repeated Stop-button tests degrading provider health further. With that
cascade no longer triggered by cancellations, this should occur far less
often. I want to be upfront that this is a reasoned inference, not a
bug I reproduced and fixed directly the way I did with #1/#2/#3.

## Bug #5: Simple prompts (e.g. "Hello") sometimes receive no response

**Not independently reproduced as a distinct new bug this session.**

Traced the same completion path as Bug #4 and found no code defect
specific to short/simple prompts — a real executed test sending exactly
`"Hello"` through the orchestrator got a correct, fast (2ms) response with
no fallback needed. The most likely explanation, consistent with the QA
session's own description of testing Stop and attachments repeatedly, is
the same health-service cascade as Bug #4. Flagging this honestly rather
than claiming a fix I can't point to a specific line of code for.
